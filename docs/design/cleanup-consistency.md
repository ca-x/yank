# 自动清理与副本一致性

## 产品行为

客户端提供简体中文、English；切换语言不修改剪贴板内容、设备名称、用户命名的分组或保存视图。语言与清理规则均属于本机偏好，不随账号覆盖其他设备。

自动清理默认关闭。开启后选择所有类型共用条目上限，或对 text/link/image/files/code/color 分别设置上限。上限只计算未收藏的有效记录；收藏记录既不占限额，也不被自动清理。可额外设置按最后修改时间过期的天数，0 表示不按天清理。条目排序按 updated 降序、id 降序稳定截断。时间只影响保留策略，不用于决定同步冲突胜负。时间漂移可能导致按天提前/推迟清理，因此默认不启用天数限制。

清理是同步删除，与手动删除范围相同：传播至已配对设备，且仅在用户启用服务端存储时传到服务端。服务端不自行运行另一套清理规则。各客户端规则互不覆盖；多个客户端采用不同上限时，任一设备都可能删除其他设备尚想保留的记录，配置界面必须说明此范围。关闭自动清理停止本机后续执行，不撤销已经产生或接收到的删除。

## DDIA 设计取舍

- SQLite WAL 单库事务：`BEGIN IMMEDIATE` 在读候选之前取得写锁，避免本机正在收藏/编辑时出现“先读后写”竞态。每批最多 200 条，以限制写锁占用。候选选择、记录写入、changes 与 outbox 在同一个事务提交，任一条失败则整批回滚；事务中不等待网络。
- 多主离线写入：保留现有版本向量、不可变逻辑写入标签、去重 operation ID、事务 outbox 和拉取游标提交机制，不引入全局锁或要求服务器在线。
- 删除是普通因果版本，保留 tombstone；已观察删除的旧版本重放不会复活记录。真正并发的编辑和删除按现有稳定逻辑顺序确定可见版本，败方保留在 conflicts，支持显式恢复。因此不承诺“删除总是胜出”或“并发收藏总是保留”。逻辑时间而非墙上时间决定冲突胜负。
- 清理设置不复制，只复制其产生的删除事实。相同事实集合和持续成功的同步最终收敛；断网期间允许各副本短暂不同，持续写入/不同规则也可能持续产生新删除，不承诺瞬间达到全局数量上限。
- 重试幂等：同一 operation ID 返回原确认；清理本身只选择未删除项，再次执行不会为已删除项重复生成写入。旧的上传确认只移除匹配 operation 的 outbox，不能误删更新后的删除操作。
- 复用已有 Protobuf 字段，不增加协议消息或修改 Buf 生成物。旧偏好 JSON 缺少 cleanup 时通过默认值获得关闭状态；不自动扩大旧版本按天清理的配置范围。

## 存储及回收边界

为类型限额增加复合索引 `(deleted,pinned,kind,updated DESC,id DESC)`；总体限额沿用现有查询索引。偏好保存前验证限额为 1..1,000,000，按类型模式须覆盖六个已知类型。未知未来类型在按类型模式下不会被数量规则删除，但可受用户选择的年龄规则影响。

当前“自动清理”指可见历史的逻辑删除，并不保证数据库文件缩小或彻底擦除敏感数据：tombstone、changes、conflicts、operations、blobs 以及旧备份仍可保留内容。禁止按固定 TTL 直接删除这些数据，否则长期离线副本可能重放并复活记录，或者破坏游标/恢复/幂等确认。

物理回收需要另一个完整方案：跟踪全部有效副本确认的因果水位，定义遗失设备的退役与重新加入协议，处理服务端关闭存储、备份恢复和副本 epoch；达到安全水位后压缩变更日志、清理无引用 blob/冲突/幂等记录并维护 tombstone 摘要。此版本不把逻辑清理宣传成物理空间回收。

## 必须验证的故障场景

关闭后不删除；总体/分类限额和年龄规则组合；收藏保护及稳定排序；200 条批次；中途失败整批回滚；跨连接并发收藏；离线副本旧数据与旧确认重放；两个客户端加服务端的删除/编辑冲突、不同到达顺序、重复传输以及显式冲突恢复；偏好升级和无效输入。

## 最近历史与使用排序

默认展示近三天，可选择当天、滚动近 1–5 天、本周（周一开始）、本月或不限日期。日历边界按本地时区计算。搜索和收藏不受默认日期限制；普通历史在当前范围耗尽后提供“加载更早的记录”。每次增加 100 条，使用 `(pinned,recency,id)` 复合游标 seek，而不是随历史增长的 OFFSET；每次刷新当前已展开窗口仍会读取已显示的全部记录，不声称恒定时间。

`recency` 是 SQLite 事务分配的本机单调逻辑序号。保存/接受同步写入或成功复制/粘贴后提前；同步来的旧记录也按本机接受顺序展示。使用事件只更新本机 `recency/activity_at`，不修改内容、版本向量、outbox 或同步日志，避免“复制了一条记录”引起多端写冲突。保留策略仍按内容 `updated` 判断，不因使用事件延长年龄。不同设备的最近使用顺序可以不同，内容与删除事实才是最终一致性目标。

整次历史窗口读取（多页及是否有更早内容）使用同一个 SQLite 延迟读事务，避免其他连接并发写入导致跨页漏项/重复；事务在查询结束时关闭，不跨越网络。查询使用总体、类型、活动时间索引；任意子串搜索仍是扫描匹配，未伪装为全文索引。迁移回填旧行后写入 schema 标记，后续打开不再重复获取该迁移写锁。升级会新增数据库列，旧版不保证可原地回退；降级应恢复升级前备份。
